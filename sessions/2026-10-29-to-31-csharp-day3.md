## 1. What is an assembly in C#?

Think of an **assembly as a compiled unit of your .NET code**.

When you build a C# project, it typically produces a `.dll` or `.exe` file. That compiled file is an assembly.

Conversely, multiple classes in the same project usually end up in the same assembly.

Remember our original example:

```csharp
public class Base
{
    private int A = 1;
    protected int B = 2;
    internal int C = 3;
```

The `internal` modifier means:

> **Code within the same assembly can access this member. Code in a different assembly generally cannot.**

Let's see how this differs from `protected`.

### Scenario A: Both classes are in the same assembly

```csharp
    internal int C = 3;

{
```

## 3. The four access modifiers to remember

| Modifier | Who can access it? |
|---|---|
| `private` | The declaring type |
| `protected` | The declaring type and derived types, subject to C# access rules |
| `internal` | Code in the same assembly |
| `public` | Any code that can access the containing type |

One extra detail for interviews: `protected internal` means access from the same assembly **or** from a derived type in another assembly. `private protected` is more restrictive: access from derived types within the same assembly.

C# deliberately doesn't support multiple **class inheritance** because it can introduce ambiguity and complexity, particularly the **Diamond Problem**.

Let's understand it with an example.

## 1. The Diamond Problem

Imagine this inheritance hierarchy:



    **Base**
    Method: Calculate()





        **Class A**
        Overrides Calculate()





        **Class B**
        Overrides Calculate()





    **Class C**
    Inherits A and B



Now suppose:

```cpp
class A : public Base { };
class B : public Base { };
class C : public A, public B { };
```

If you call:

```cpp
C obj;
obj.Calculate();
```

Which implementation should execute?

- `A.Calculate()`?
- `B.Calculate()`?
- `Base.Calculate()`?

This creates ambiguity unless the language provides additional rules or mechanisms to resolve it.

C++ supports multiple inheritance and has mechanisms such as virtual inheritance to address the diamond problem. C# chose not to support multiple class inheritance.

## 2. How does C# solve this?

C# allows:

- Inheriting from exactly one class.
- Implementing multiple interfaces.

```csharp
interface ILogger
{
    void Log();
}

interface IRetryable
{
    void Retry();
}

class Notification : SomeExistingBaseClass,
                     ILogger,
                     IRetryable
{
    public void Log() { }
    public void Retry() { }
}
```

You can also reuse implementation through **composition**:

```csharp
class Notification
{
    private readonly RetryHandler retryHandler;
    private readonly Logger logger;

    public Notification()
    {
        retryHandler = new RetryHandler();
        logger = new Logger();
    }
}
```

Here, `Notification` uses functionality from multiple objects without inheriting from multiple classes.

## 3. Interview takeaway

| Mechanism | Purpose |
|---|---|
| Inheritance | Reuse and specialize a class |
| Interfaces | Define multiple contracts |
| Composition | Reuse functionality from multiple objects |
| Abstract classes | Share state and implementation among related classes |

**One important nuance:** The diamond problem isn't the only reason for C#'s design choice. Multiple inheritance also complicates state layout, method resolution, and object initialization.

This is a very important distributed-systems problem called **duplicate delivery**. Let's build the intuition.

## 1. What went wrong?

Imagine this sequence:


  Primary email provider receives the request.
  Primary successfully sends the email to the recipient.
  Its response gets lost or times out before reaching our application.
  Our application assumes delivery failed and invokes the backup provider.
  Backup sends the same email again.


Result: Duplicate email

The important distinction is:

**A timeout does not necessarily mean the operation failed. It means we don't know whether it succeeded.**

This is called an *ambiguous outcome*.

## 2. How do we prevent duplicate delivery?

Use an **idempotency key**.

Every logical notification gets a unique ID, for example:

```csharp
var notificationId = Guid.NewGuid();
```

Both providers receive the same ID:

```csharp
primary.Send(notificationId, recipient, message);
backup.Send(notificationId, recipient, message);
```

The receiving provider or a shared delivery system records processed IDs.

If it receives the same ID again, it recognizes that the notification was already processed and avoids sending it again.

Conceptually:



    **Notification ID: N-123**





        **Primary**
        Delivered




        **Backup**
        Same ID detected



  A shared idempotency mechanism can prevent duplicate processing.


One important caveat: this works only if the provider or a downstream delivery system actually supports idempotency. Merely generating a GUID in our application doesn't prevent duplicates.

Even with idempotency, exactly-once delivery across independent email providers generally cannot be guaranteed. We can build effectively-once processing within defined boundaries.

## 3. Interview takeaway

Remember these three concepts:

| Concept | Meaning |
|---|---|
| At-most-once | Don't deliver duplicates, but messages may be lost |
| At-least-once | Retry until acknowledged, but duplicates are possible |
| Idempotency | Repeated processing of the same logical request has no additional effect |

# Day 3 — Topic 1: `this` keyword

The `this` keyword refers to the **current instance of the class**.

It is commonly used for three purposes:

1. Distinguishing instance fields from parameters.
2. Calling another constructor in the same class.
3. Passing the current object as an argument.

## 1. `this` to distinguish fields and parameters

Consider:

```csharp
public class Employee
{
    private string name;

    public Employee(string name)
    {
        this.name = name;
    }
}
```

Here:
- `name` refers to the constructor parameter.
- `this.name` refers to the instance field.

Without `this`, the assignment `name = name` would assign the parameter to itself.

## 2. `this()` — constructor chaining

One constructor can call another constructor in the same class using `this()`.

```csharp
public class Employee
{
    private string name;
    private int age;

    public Employee() : this("Unknown", 0)
    {
    }

    public Employee(string name) : this(name, 0)
    {
    }

    public Employee(string name, int age)
    {
        this.name = name;
        this.age = age;
    }
}
```

Consider these object creations:

```csharp
var e1 = new Employee();
var e2 = new Employee("Shivam");
var e3 = new Employee("Shivam", 23);
```


  **Constructor execution flow**


    `new Employee()`





    `Employee("Unknown", 0)`

  The target constructor executes first; then the original constructor body executes.


**Important:** Constructor chaining avoids duplicating initialization logic.

## 3. `this()` vs `base()`

These are different:

| Syntax | Purpose |
|---|---|
| `this(...)` | Calls another constructor in the same class |
| `base(...)` | Calls a constructor in the parent class |

A constructor can explicitly use either `this()` or `base()`, but not both in the same constructor initializer. A chain through `this()` can eventually call a base constructor.

## 4. Important rules

- Constructor chaining must appear in the constructor initializer, after `:`.
- It must be the first constructor action.
- Circular constructor chains are invalid.
- The target constructor executes before the calling constructor's body.
- `this` cannot be used in a static method because there is no current instance.

# Day 3 — Interface Segregation Principle (ISP)

Let's understand this using the notification system we just designed.

## 1. The problem ISP solves

The **Interface Segregation Principle** states:

> Clients should not be forced to depend on interfaces they do not use.

In simpler terms: Don't create one large interface that forces every implementation to implement irrelevant methods.

### Consider this interface

```csharp
public interface INotificationService
{
    Task SendEmail(string message);
    Task SendSms(string message);
    Task SendPushNotification(string message);
}
```

Now imagine implementing an email service:

```csharp
public class EmailNotificationService : INotificationService
{
    public Task SendEmail(string message)
    {
        // Send email
        return Task.CompletedTask;
    }

    public Task SendSms(string message)
    {
        throw new NotImplementedException();
    }

    public Task SendPushNotification(string message)
    {
        throw new NotImplementedException();
    }
}
```

What's wrong?

- Email service is forced to implement SMS functionality.
- It contains methods that are irrelevant to its responsibility.
- Consumers may accidentally call unsupported operations.
- Adding more notification channels makes the interface increasingly bloated.

This is an ISP violation.

## 2. Applying ISP

Instead of one large interface, split it into smaller, capability-specific interfaces.

```csharp
public interface IEmailNotification
{
    Task SendEmail(string message);
}

public interface ISmsNotification
{
    Task SendSms(string message);
}

public interface IPushNotification
{
    Task SendPushNotification(string message);
}
```

Implement only the capabilities a class actually supports:

```csharp
public class EmailNotificationService : IEmailNotification
{
    public Task SendEmail(string message)
    {
        // Send email
        return Task.CompletedTask;
    }
}
```

A service supporting multiple channels can implement multiple interfaces:

```csharp
public class MultiChannelNotificationService :
    IEmailNotification,
    ISmsNotification
{
    public Task SendEmail(string message)
    {
        return Task.CompletedTask;
    }

    public Task SendSms(string message)
    {
        return Task.CompletedTask;
    }
}
```

## 3. Does this mean every interface should have only one method?

No. That's a common misunderstanding.

An interface can have multiple methods if they represent a cohesive responsibility or capability.

For example:

```csharp
public interface IEmailNotification
{
    Task Send(string recipient, string message);
    Task SendWithAttachment(
        string recipient,
        string message,
        byte[] attachment);
}
```

Both operations are related to email delivery, so they can reasonably belong together.

The goal is **cohesion**, not minimizing the number of methods at all costs.
